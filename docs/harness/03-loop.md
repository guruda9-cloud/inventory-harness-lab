# 구현 루프 — 재고관리 PoC

> SSOT §4의 원본. "구현 루프"는 유지보수 Issue 하나를 시작부터 종료(검증 통과 또는
> `NEED_HUMAN`)까지 진행하는 절차 전체를 말한다. [`02-verification.md`](02-verification.md)(§3
> 검증)가 "지금 결과가 참인지 거짓인지"만 판정한다면, 이 문서는 "실패했을 때 다시
> 시도할지, 몇 번째 시도인지, 세션이 끊겼을 때 어디서 이어갈지, PR·CI로 넘어간 뒤에는
> 어떻게 이어갈지"를 다룬다 — **판정과 재시도 관리를 서로 다른 책임으로 분리한다.**

---

## 0. 책임 분리

| 관심사 | 담당 | 산출물 |
|---|---|---|
| 지금 결과가 통과인지 실패인지, 어느 단계에서 실패했는지 | §3 검증 (`npm run verify`, 로컬이든 CI든) | 종료 코드, 실패 단계 이름 |
| 실패 시 다시 시도할지, 몇 번째 시도인지, 세션이 끊기면 어디서 이어갈지 | §4 구현 루프 (본 문서) | GitHub Issue·PR 코멘트 |

검증은 재시도 여부를 스스로 판단하지 않는다. 검증은 판정만 하고, 그 판정을 받아
재시도·중단·`NEED_HUMAN` 전환을 결정하는 것은 전부 이 문서의 규칙을 따른다.

---

## 1. 시도(attempt)의 정의

**"코드 수정 + `npm run verify` 1회 실행"까지를 묶어 1시도로 센다.**

- 코드만 고치고 `npm run verify`를 아직 실행하지 않은 상태는 시도로 세지 않는다
- `npm run verify`를 실행한 순간 그 시도는 소모된 것으로 기록한다 — 통과든 실패든 무관하다
- 같은 시도 안에서 여러 파일을 고쳐도 좋다. **verify 실행 1회당 1시도**이지, 파일
  수정 횟수나 커밋 횟수가 아니다
- PR이 열린 뒤(§2.5)에는 `npm run verify`가 이 세션이 아니라 **CI**에서 돌지만, 정의와
  카운터는 그대로다. CI 전용 카운터를 따로 두지 않는다 — PR 여부는 검증을 어디서
  실행하는지만 바꿀 뿐, 시도를 세는 방식은 바꾸지 않는다

최대 시도 횟수는 Issue-SSOT 규칙(SSOT §0)에 따라 **그 Issue Form §6("구현 루프 최대
횟수")이 정한 값**을 그대로 쓴다. 이 문서는 횟수를 세는 방법과 기록하는 방법만
정의하고, 몇 회가 적절한지는 Issue마다 다르게 정한다.

---

## 2. 세션 복구 — GitHub 코멘트가 SSOT

에이전트 세션이 끊기면 대화 컨텍스트 안에 있던 "지금까지 몇 번 시도했다"는 정보도
함께 사라진다. 하네스 자체에는 이를 대신 저장하는 상태 파일·DB가 없다. 이 문제를
풀기 위해 **진행 상황의 SSOT를 대화가 아니라 코멘트로 둔다** — PR이 열리기 전에는
Issue 코멘트, 열린 뒤에는 PR 코멘트다 (§2.5).

### 2.1 시작할 때 — 이어서 할지 새로 시작할지 판단

이슈 작업을 시작하기 전, 에이전트는 항상 먼저 진행 상황을 조회한다.

```
gh issue view {번호} --comments
```

이미 연결된 PR이 있다면(§2.5) Issue 코멘트 대신 **그 PR의 코멘트 + CI 상태**를 본다.

```
gh pr view {PR 번호} --comments
gh pr checks {PR 번호}
```

`<!-- agent-loop:issue-{번호} ... -->` 마커가 붙은 코멘트가 있으면, 그중 **가장
최근 것**을 마지막 상태로 본다.

- `result=pass|fail`이면 그 `attempt` 값 다음 번호부터 이어서 센다
- `result=reset`이면 그 코멘트가 이미 시도 횟수를 0으로 되돌린 것이므로, 다음 시도를
  1로 보고 이어서 센다
- `result=need_human`이면 **사람의 새 지시 없이는 재시도하지 않는다.** `reason`이
  `ssot_conflict`/`scope_ambiguous`이고 사람이 이미 새 지시를 줬다면 §2.4-①에 따라
  초기화 코멘트를 먼저 남긴 뒤 시도 1부터 재개한다. `reason`이 `attempts_exhausted`면
  Issue Form §6 값이 사람 손으로 바뀌기 전까지 재시도하지 않는다 (§2.4-②)
- `result=closed`(`reason=requirement_change`)면 **이 Issue는 끝난 것이다.** 재개하지
  않는다 — 사람이 새 Issue를 올렸는지 확인하고, 있다면 그 Issue로 작업한다 (§2.4-③)
- 마커가 하나도 없으면 시도 0부터 새로 시작한다

### 2.2 매 시도 직후 — 결과를 코멘트로 남긴다

`npm run verify`를 실행한 직후(통과·실패 관계없이, 로컬이든 CI든) 아래 형식으로
코멘트를 남긴다. 첫 줄의 HTML 주석은 화면에는 보이지 않고 다음 세션이 파싱해
이어가기 위한 마커다.

```
<!-- agent-loop:issue-{번호} attempt={k} max={max} result={pass|fail} -->
### 구현 루프 — 시도 {k}/{max}
- 실행: `npm run verify` (로컬 / CI)
- 결과: 통과 / 실패 (실패 단계: typecheck|lint|architecture|test|build)
- 실패 원인: {한두 줄 요약, 실패라면}
- 다음 조치: 재시도 / NEED_HUMAN ({사유})
```

### 2.3 종료 조건과 NEED_HUMAN 사유

- **통과** → Pre-PR이면 §2.5로 (PR을 연다), Post-PR(CI)이면 완료를 기록하고 루프를
  끝낸다 (이후 PR 리뷰·머지는 사람의 몫, SSOT §0-1)
- **실패했고 시도 횟수가 남아 있다** → 코드 수정 단계(§2.6)에서 원인을 분석하고 다음
  시도로 넘어간다
- **더 진행할 수 없어 `NEED_HUMAN`으로 전환한다** → 아래 세 갈래를 구분해 코멘트에
  사유를 명시한다. 임의로 최대 횟수를 늘리거나 조용히 계속 시도하지 않는다 (SSOT §0)

  | 사유 | 언제 | `reason` 값 | 재개 방식 |
  |---|---|---|---|
  | SSOT·이슈 해석 문제 | SSOT §0 문서 충돌, 또는 이 Issue의 종료 조건(Form §3)·범위 해석이 모호해 임의로 진행할 수 없는 경우 | `ssot_conflict` / `scope_ambiguous` | 사람 지시 후 reset, 같은 Issue에서 재개 (§2.4-①) |
  | 반복 실패로 소진 | 검증이 계속 실패하고 최대 시도 횟수를 다 쓴 경우 | `attempts_exhausted` | 사람이 Form §6 값을 직접 바꿔야 재개 (§2.4-②) |
  | 요건·범위 변경 필요 | 이 실패를 해결하려면 Issue Form §5·§5-1(건드리면 안 되는 것)을 넘어서거나, SSOT §1·§2(요구사항·아키텍처) 자체를 고치거나, 지금 존재하지 않는 새 상태·스키마·비즈니스 규칙을 만들어야 하는 경우 | `requirement_change` | 재개 없음 — 이 Issue 종료, 새 Issue 필요 (§2.4-③) |

  이 세 갈래를 코드 수정 단계에서 실제로 가르는 기준은 §2.6을 따른다. 로컬 verify
  실패든 PR의 CI 실패든 같은 기준을 쓴다 — CI 전용 사유를 따로 두지 않는다.

  ```
  <!-- agent-loop:issue-{번호} attempt={k} max={max} result=need_human reason={ssot_conflict|scope_ambiguous|attempts_exhausted|requirement_change} -->
  ### NEED_HUMAN — 시도 {k}/{max}
  - 사유: {ssot_conflict | scope_ambiguous | attempts_exhausted | requirement_change}
  - 무엇이 왜 갈렸는지: {요약}
  - 필요한 결정: {사람이 정해줘야 하는 것}
  ```

### 2.4 NEED_HUMAN 이후 — 사유별 재개 규칙

세 사유는 재개 방식이 서로 다르다. 하나로 뭉뚱그리지 않는다.

**① `ssot_conflict` / `scope_ambiguous` — 사람 지시 후 reset, 같은 Issue에서 재개**

사람이 새 지시(요구사항 해석·범위 확정 등)를 내리면, 그 지시는 이전까지의 시도들이
풀지 못했던 **판단 문제를 해소한 것**이지 "코드를 더 고쳐보라"는 뜻이 아니다. 그래서
이 경우 에이전트는 **다음 시도부터 시도 횟수를 0으로 초기화**하고, 다시 최대 횟수만큼
시도할 수 있다.

- 사람은 코멘트로 답해도 되고, **Issue 본문(Form §2·§3 등)을 직접 고쳐서 답해도
  된다.** 다만 §2.1의 재개 로직은 **코멘트만 조회**하므로, 본문만 고치고 코멘트를
  남기지 않으면 다음 세션이 그 변경을 놓칠 수 있다. **그래서 이슈 본문을 고쳤다면
  그 사실을 알리는 코멘트도 함께 남긴다** (예: "Form §3을 수정했습니다 — 확인 후
  재개해주세요"). 이 코멘트가 없으면 에이전트는 마지막 마커가 여전히 `need_human`인
  것으로 보고 계속 대기한다
- **초기화도 반드시 코멘트로 남긴다** — 다음 세션이 마지막 코멘트만 보고도 "왜 시도
  횟수가 다시 0부터인지" 알 수 있어야 한다

  ```
  <!-- agent-loop:issue-{번호} attempt=0 max={max} result=reset reason={ssot_conflict|scope_ambiguous} -->
  ### 구현 루프 — 시도 횟수 초기화
  - 이전 상태: NEED_HUMAN (사유: {ssot_conflict|scope_ambiguous}, 시도 {k}/{max}였음)
  - 사람의 새 지시: {요약, 또는 "Issue 본문 §N 수정"}
  - 시도 횟수를 0/{max}으로 초기화하고 재개한다
  ```

- 초기화 이후 다음 verify 실행은 다시 **시도 1/{max}**부터 코멘트를 남긴다

**② `attempts_exhausted` — 초기화 없음, Form §6 값을 사람이 직접 바꿔야 재개**

이미 코드 수정 기회를 다 쓴 것이므로, 사람이 무언가 지시를 주더라도 이 문서의
규칙만으로 자동 초기화하지 않는다. 최대 횟수 자체를 늘려야 한다면 그 Issue Form §6
값을 사람이 고쳐야 한다 (Issue-SSOT 규칙, SSOT §0). 값이 바뀐 걸 확인하면 그때
시도 1부터(또는 마지막 시도 다음 번호부터) 재개한다.

**③ `requirement_change` — 재개 없음, 이 Issue 종료**

앞의 두 사유와 달리 "사람이 새 지시를 냄?"을 거치지 않는다. 물을 게 없기
때문이다 — 요구사항·범위 자체가 바뀌어야 한다는 게 이미 드러난 상태라, 사람이 뭐라
답하든 **이 Issue의 범위 안에서는 풀리지 않는다.** NEED_HUMAN 코멘트 직후 바로 종료를
기록하고 루프를 끝낸다.

```
<!-- agent-loop:issue-{번호} attempt={k} max={max} result=closed reason=requirement_change -->
### 구현 루프 — 이 Issue 종료
- 사유: requirement_change
- 무엇을 바꿔야 하는지: {요약}
- 다음 조치: 사람이 새 Issue를 만들어 변경된 요구사항·범위를 다룬다
```

같은 Issue 번호로 다시 시도하지 않는다. PR이 이미 열려 있었다면 그 PR도 함께
정리한다(닫거나 draft로 남기는 판단은 사람 몫).

### 2.5 PR·CI 단계 — 기록 위치 전환 (Phase)

로컬 verify가 통과하면(Pre-PR) 루프가 끝나는 게 아니라 **PR로 넘어간다.**

- **PR 진입**: 통과를 기록한 직후 자동으로 브랜치를 push하고 PR을 연다. PR 본문에
  이 Issue를 연결한다(`Closes #N`)
- **기록 위치 전환**: PR이 열리는 순간 **Phase가 Post-PR로 바뀌고, 그 이후 진행
  상황은 PR 코멘트에 남긴다.** Issue에는 "→ PR #N에서 이어감" 한 줄만 마지막으로
  남기고 멈춘다 — 세션이 봐야 할 곳을 항상 하나로 유지하기 위해서다 (다음 세션의
  조회 방법은 §2.1)
- **CI = 같은 검증, 다른 실행 위치**: PR에 push하면 CI가 자동으로 트리거되고, CI는
  로컬과 **똑같은 `npm run verify`**를 실행한다(02-verification.md §4). "PR 단계의
  검증"이라는 별도 개념은 없다 — PR은 검증을 CI에서 대신 실행하게 만드는 트리거일
  뿐이다
- **CI 통과** → 완료. 이후 PR 리뷰·머지는 항상 사람이 한다 (SSOT §0-1, "애플리케이션
  코드 최종 승인: 사람"). 이 문서는 PR을 열고 코멘트를 남기는 것까지만 다룬다
- **CI 실패** → §2.3의 "실패했고 시도 횟수가 남아 있다"와 완전히 동일하게 취급한다.
  같은 attempt 카운터에서 1회 소모하고, §2.6 기준으로 원인을 분류한다. CI 실패
  전용 사유(예: 환경 차이)는 두지 않는다

### 2.6 실패 원인 분류 — 코드 수정 단계의 판단 기준

코드 수정 단계는 최초 시도든 재시도든, 로컬 실패든 CI 실패든 **항상 거치는 진단
지점**이다. 여기서 아래 2단계 질문을 순서대로 물어 실패 원인을 가른다 — 1단계에서
"아니오"가 나올 때만 2단계로 넘어간다.

| 단계 | 질문 | 예 | 아니오 |
|---|---|---|---|
| 1 | 정답이 Issue Form §2(변경할 내용)·§3(종료조건) + 기존 요구사항·아키텍처(SSOT §1·§2)만으로 이미 하나로 정해지는가? | → **`AI 구현 오류`** — 정답은 이미 정해져 있다, 코드만 못 따라갔다. 같은 범위에서 재시도 (§2.3의 일반 재시도 경로) | 2단계로 |
| 2 | 그 모호함을 Issue Form §5·§5-1(건드리면 안 되는 것) 범위 밖으로 나가지 않고, 이미 문서 어딘가에 있는 답 중 하나를 사람이 골라주는 것만으로 풀 수 있는가? | → **`scope_ambiguous`/`ssot_conflict`** — 정답이 문서 안에 있는데 읽는 것만으로는 어느 쪽인지 못 고른다. 해결 후에도 범위·요구사항 문서 자체는 그대로 (§2.4-①) | → **`requirement_change`** — 정답대로 하려면 §5·§5-1에서 건드리지 말라던 것을 건드리거나, SSOT §1·§2 자체를 고치거나, 지금 없는 새 상태·스키마·비즈니스 규칙을 만들어야 한다 (§2.4-③) |

## 3. 이 문서가 다루지 않는 것

- 무엇을 통과로 볼지(불변식·Issue 종료 조건 판정) → §3 검증, [`02-verification.md`](02-verification.md)
- 최대 시도 횟수가 몇 회여야 하는지 → 개별 Issue Form §6
- 코드 변경 범위·건드리면 안 되는 것 → 개별 Issue Form §5·§5-1
- PR 리뷰·머지 여부 → 항상 사람이 결정한다 (SSOT §0-1)
- 마일스톤별 구현 현황·알려진 함정 → [`docs/HANDOVER.md`](../HANDOVER.md)
