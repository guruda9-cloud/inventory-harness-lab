## 0. 문서 충돌 시 판단 규칙

판단이 갈리는 순간 임의로 해소하지 않고 사람에게 넘기기 위한 경계선.

- Issue가 요구사항·아키텍처·하네스 규칙과 충돌하면 **중단**하고 사람에게 넘긴다
- **충돌하지 않는 한, 개별 작업의 범위 안에서는 그 작업의 Issue가 SSOT다.** 배경·변경할 내용·종료 조건·기계 검증·건드리면 안 되는 것·구현 루프 최대 횟수(`.github/ISSUE_TEMPLATE/maintenance.yml`의 6개 항목)는 요구사항(1절)·아키텍처(2절)가 정하지 않은 세부 사항을 그 Issue가 확정한다 — 다른 Issue나 과거 관행을 끌어와 임의로 범위를 넓히거나 좁히지 않는다. 이 Issue-SSOT는 1·2절보다 하위이므로 충돌 시 위 규칙(중단)이 항상 우선한다
- 참고문서(02~05, 07 등)가 SSOT(본 문서 1·2절)와 다르면 **SSOT를 따른다**
- 계획 문서(07-plan.md 등)와 요구사항(1절)이 다르면 **요구사항을 따른다**
- SSOT가 2개 이상 존재하고 서로 충돌하면, 사람이 기준을 고치기 전까지 **구현하지 않는다**

> **에이전트의 임의 충돌 해소 = 판단 기준 1개 삭제.** 충돌을 발견하면 조용히 하나를 택하지 말고, 반드시 사람을 호출해 알린다.

**사람의 판단이 필요한 경우 `NEED_HUMAN` 상태를 선언한다.** 임의로 진행하지 않고 작업을 멈춘 뒤, 무엇이 왜 갈렸는지를 명시해 사람에게 넘긴다.

## 0-1. 보호 영역과 소유권

영역별 읽기 권한과 변경 권한을 분리한다.

| 영역 | AI | 사람 |
|---|---|---|
| 애플리케이션 코드 | Issue 범위 안에서 수정 | 최종 승인 |
| Issue별 테스트 | 작성·수정 | 전제 검토 |
| 요구사항·아키텍처 (본 SSOT 1·2절) | 읽기 | 변경·승인 |
| 하네스 핵심 규칙 (0·0-1절) | 읽기 | 변경·승인 |
| 검증 스크립트 | 실행 | 정책 변경 승인 |

AI는 요구사항·아키텍처·하네스 핵심 규칙·검증 스크립트의 정책을 **스스로 고치지 않는다** — 읽고 따르거나 실행만 하고, 바꿔야 한다고 판단되면 사람에게 변경을 요청한다.

## 1. 요구사항

> 원본: [`01-requirements.md`](../01-requirements.md)

- **정의**: 풀필먼트 3사 + 자사창고에 흩어진 재고를 FEFO로 관리하고, 팝업 반출·반입까지 추적하는 사내 재고관리 앱
- **Lot = SKU × 거점 × 유통기한**. 셋 중 하나라도 다르면 다른 재고
- **거점 5종**: 자사창고(직접 셈) · 풀필먼트A/B/C(저쪽 수치가 진실) · 팝업(임시, 종료 시 잔여 0) · 배송 중(가상) · 폐기(가상) — 가상 거점을 두는 이유: 재고를 "사라지는" 상태로 만들지 않기 위해서 (§2.1 참조)

### 기능 요구사항 (F1~F11)

| ID | 핵심 규칙 |
|---|---|
| F1 | 상품별 유통기한 경고 임계일 설정 가능 |
| F2 | 거점 추가/수정, 팝업 거점은 행사 단위 생성·종료 후 비활성화 |
| F3 | SKU별 전체 수량 + 거점별 분해, 임박 강조 |
| F4 | 입고 시 유통기한 단위로 로트 생성/합산 |
| F5 | 출고는 **사유 필수 + FEFO 강제**, 다른 로트 선택 시 사유 필수 |
| F6 | 자사창고→풀필먼트 이동은 2단계(발송→도착확인), **발송만 LEFO** (§2.3 참조) |
| F7 | 팝업: 반출(FEFO, 여러 번 가능) → 반입 시 잔여만 입력 → `반출−반입=판매` 역산, 시식/판매 구분 |
| F8 | 재고 조정(실사)은 사유 필수, 이력 삭제 불가 |
| F9 | 유통기한 만료는 **자동 폐기 없음**, 사람이 확정. 알림은 앱 내 표시만 |
| F10 | 모든 수량 변화는 Movement로 기록, 수정·삭제 불가, 취소는 상쇄 기록 |
| F11 | 로그인 필수(관리자가 계정 등록), 모든 기록에 작성자 남음 |

**사유 코드 (F5-1)** — 감소: `SALE`(기본)·`SAMPLE`·`DAMAGE`·`LOSS`·`DISPOSE`·`OTHER` / 증가: `PURCHASE`(기본)·`RETURN`·`OTHER` / 조정 전용: `COUNT_DIFF`·`INPUT_ERROR`. `OTHER`는 메모 필수. **위치 이동**(발송·도착·팝업 반출·팝업 복귀)은 총 재고 불변이라 사유 없음 — 팝업 정산에서 사유가 붙는 건 안 돌아온 수량(판매/시식)뿐. 전체 표는 01 §F5-1 참조.

**비기능 요구사항 핵심**: 재고 음수 금지(트랜잭션 필수) · 삭제 대신 상쇄 기록 · 색만으로 상태 구분 금지(텍스트 병기) · 한글 IME 대응 · SQLite 백업 절차 필요. 전체는 01 §5 참조.

**Out of Scope**: 풀필먼트 API 연동, CSV 대조, 바코드/QR, 로트번호(입고 배치) 추적, 팝업 중 판매 건별 기록, 발주/원가/매출, 권한 세분화, 다국어, 오프라인. (01 §6)

**완료 기준(DoD)**: 로트 분리·FEFO 자동선택·발송 중 총재고 불변·FEFO↔LEFO 반대 동작·팝업 역산·사유별 집계 분리·실사 사유 필수·임박 알림·모바일 반응형·이력 추적·데이터 영속성. 12개 항목 전문은 01 §7 참조.

## 2. 아키텍처

> 원본: [`06-architecture.md`](../06-architecture.md)

**스택**: Next.js 16(App Router) + TypeScript + Prisma/SQLite(WAL) + Tailwind, 자체 세션 쿠키(jose+bcryptjs), 클라이언트 상태관리 없음(서버가 진실), 테스트 Vitest. (06 §1)

### 2.1 데이터 모델

핵심 엔티티: `User · Product · Location · Lot · Movement · Transfer/TransferLine · Popup/PopupPlan`.

- `Lot`은 `@@unique(productId, locationId, expiryDate)`로 로트 정의를 DB 제약으로 강제
- **`Movement`가 이력의 진실**, `Lot.quantity`는 그 결과를 빠르게 읽는 현재값. 항상 같은 트랜잭션에서 갱신
- `Movement.from/to`가 둘 다 내부 거점이면 총 재고 불변, 한쪽이 `null`(외부)이면 그때만 총량 변화 — 이 원칙이 §2.4 불변식의 근거
- 취소는 삭제가 아니라 `reversalOfId`로 원본을 가리키는 반대 방향 Movement. 원본당 상쇄는 1회만 허용

전체 스키마·필드는 06 §3 참조.

### 2.2 재고 변경의 유일한 통로

`lib/stock.ts`의 **`applyMovement()`** 한 곳에서만 Lot을 갱신한다. ① 출발지 차감(부족하면 예외, 아무것도 안 바뀜) ② 도착지 가산(upsert) ③ Movement 기록 — 세 단계가 한 트랜잭션. 화면/액션은 `lot.update()`를 직접 호출하지 않는다. 구현 코드는 06 §4.1 참조.

### 2.3 로트 배분 — FEFO / LEFO

> 01·06에 중복돼 있던 표를 이 한 곳으로 통합.

| 동작 | 전략 | 이유 |
|---|---|---|
| 출고·풀필먼트 일일 반영·팝업 반출 | **FEFO** (임박 먼저) | 곧 소비되므로 먼저 내보내야 안 버린다 |
| **풀필먼트 발송** | **LEFO** (넉넉한 것 먼저) | 도착 3~5일+판매 대기 — 임박분을 보내면 팔리기 전에 만료 |
| 폐기 | 만료분 지정 | — |

`lib/fefo.ts`의 `planAllocation(lots, qty, strategy)` 하나로 양방향 처리. 규칙: 한 거점 안에서만 배분·만료 로트도 후보 포함·LEFO에서 넉넉한 재고 부족 시 임박분 경고 표시·수동 선택은 사유 필수. 구현 코드는 06 §4.2 참조.

### 2.4 팝업 정산 · 취소

- **정산**: `settlePopupTx()`가 누적 반출(모든 POPUP_OUT − 기존 POPUP_IN) 기준으로 `차감 = 누적반출 − 반입`, `판매 = 차감 − 시식`을 계산해 판매(외부)/시식(외부)/잔여(자사창고 복귀)로 각각 `applyMovement` 호출. 1차 반출만 놓고 계산하면 틀리므로 **반드시 누적 기준**
- **취소**: `reverseMovement()`가 상쇄 Movement 생성, 중복 상쇄는 트랜잭션 내 체크로 거부
- 공식·코드는 06 §4.3~4.4 참조

### 2.5 인증 · 동시성

- JWT 쿠키(httpOnly, 7일), `middleware.ts`가 비로그인 시 `/login`, Server Action마다 세션에서 `userId`를 Movement에 기록. 역할(`role`)은 필드만 있고 기능 차이 없음
- SQLite WAL 모드, 2~3명 규모라 쓰기 충돌 사실상 없음(충돌 시 재시도 1회), `Lot(locationId, expiryDate)` 인덱스로 FEFO 조회 최적화

### 2.6 핵심 불변식 (검증 대상)

| ID | 불변식 |
|---|---|
| INV-1 | FEFO는 항상 임박 로트부터 배분한다 |
| INV-2 | 여러 로트에 걸친 수량은 정확히 쪼개 배분한다 |
| INV-3 | 재고 초과 출고는 예외를 던지고 아무것도 바뀌지 않는다 |
| INV-4 | 발송→도착확인 전후 총 재고 합계가 같다 |
| INV-5 | 팝업 정산은 누적 반출 기준으로 역산된다 |
| INV-6 | 시식 수량이 차감분보다 크면 저장되지 않는다 |
| INV-7 | 취소(상쇄) 후 로트 수량이 원복된다 |

대상 테스트 파일은 06 §9 참조.

## 3. 검증

> 원본: [`02-verification.md`](02-verification.md)

- **자동**: `npm run verify` 한 줄이 `prepare → typecheck → lint → architecture → test → build` 순서로 돈다. PR·`main` push마다 `.github/workflows/verify.yml`이 동일 명령을 실행한다
- `verify:prepare`가 로컬 DB를 지우고 같은 시드로 재생성해, 매번 동일한 상태에서 검증이 시작된다 (기존 로컬 조작 상태에 결과가 흔들리지 않음)
- `test` 단계는 INV-1~7을 `tests/*.test.ts`로 검증한다(§2.6 표와 동일)
- 개별 Issue의 종료 조건(§0 Issue-SSOT 규칙)은 `tests/issues/issue-{번호}-{기능명}.test.ts`로 검증하며, `vitest.config.ts`의 `tests/**/*.test.ts` 패턴에 포함돼 별도 설정 없이 `test` 단계에서 함께 돈다 — 02 §2-1 참조
- `architecture` 단계(`scripts/verify-architecture.ts`)는 §2.2(재고 변경 유일 통로)·§7.5(Prisma 서버 전용) 위반을 정적으로 검사해 위반 시 실패한다
- **수동**: QA 체크리스트(반응형·엣지케이스·페르소나 시나리오)는 자동화 대상이 아니다 — 02 §5 참조
- 전체 표·CI 세부 설정은 02 참조
